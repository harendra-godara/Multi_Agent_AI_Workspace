1. Project Overview

The Multi-Agent AI Workspace is a collaborative platform where users create workspaces, define tasks, and delegate work to AI agents that execute those tasks and produce artifacts (files, outputs, reports). A user signs up, creates a workspace, invites collaborators, creates tasks, and assigns some of those tasks to an AI agent instead of a human. The AI Agent Service reasons about the task, decides what actions are needed, and calls the Execution & Artifact Service to actually run those actions in a sandbox. The result — logs, files, structured output — is stored as an artifact and linked back to the task, so the human who created it can review the outcome from the frontend.

The system was originally specified as four independent microservices (Identity & Access, Workspace & Task, AI Agent, Execution & Artifact) plus a frontend, each with its own process, deployment, and possibly its own datastore. Because one contributor (Harendra) is solely responsible for two of those four backend services, those two have been consolidated into a single modular Express application. The reasoning for this is explained in detail in Section 5 — in short, the *logical* separation (auth vs. workspace/task logic) is preserved in code and schema, but the *physical* separation (two servers, two deployments, network calls between them) is dropped because it adds operational cost without adding value for a single developer.

2. Goals & Objectives

  • Deliver a working end-to-end platform: user signs up → creates a workspace → assigns tasks to AI agents → agents execute and produce artifacts → results are visible in the workspace.
  • Demonstrate solid backend fundamentals: authentication, authorization, relational data modeling, and secure API design — the kind of thing that would hold up in a real production system, not just a demo.
  • For Harendra specifically: use this project as a learning vehicle. Every architectural and technical decision is documented with reasoning in docs/PROGRESS.md, not just implemented and forgotten.
  • Keep the system modular enough that the Identity & Access and Workspace & Task services could be physically split into two real microservices later, with minimal rework, if the project ever needs to scale that way.
  • Ensure the four backend services + frontend can be integrated by four different people without constant back-and-forth, by defining clear API contracts up front (see Section 9).

3. Scope

3.1 In Scope

  • User identity, registration, authentication, and session management
  • Workspace creation, membership management, and role-based access within a workspace
  • Task creation, assignment (to a human or an AI agent), dependency chains, and status tracking
  • Workflow runs — linking a task to one execution attempt by an AI agent, with status and result tracking
  • AI agent orchestration: interpreting a task, planning steps, invoking tools/actions
  • Execution sandboxing and artifact storage/retrieval
  • Frontend UI for auth, workspace management, task boards, and artifact viewing

3.2 Out of Scope (v1)

  • Billing / payments / subscription tiers
  • Multi-tenant organization hierarchy above the workspace level (e.g. "companies" containing multiple workspaces)
  • Real-time collaborative editing (e.g. simultaneous cursors, live presence indicators)
  • Mobile native apps (web-responsive frontend only)
  • Third-party OAuth login (Google/GitHub sign-in) — email/password only for v1
  • Rate limiting / abuse prevention at the infrastructure level (acceptable to note as a known gap for a student project)

5. System Architecture

Original spec: Four independent microservices (Identity & Access, Workspace & Task, AI Agent, Execution & Artifact), each its own deployable unit, communicating over HTTP (and possibly a message queue for async agent work), with a separate frontend calling into all of them.

Adapted approach: Identity & Access and Workspace & Task — both owned by Harendra — are combined into a single modular Express application. The AI Agent Service and Execution & Artifact Service remain separate, owned by teammates.

Why consolidate two of them:

  • No isolation benefit for a single owner. Microservices earn their complexity when different teams need to deploy independently, scale independently, or use different tech stacks. Here, one person writes and deploys both services — the "independence" of separate processes buys nothing.
  • Lower operational overhead. Two services would mean two package.jsons, two servers to run locally, two sets of environment variables, and a network call (with its own failure modes — timeouts, retries, serialization) for what is really just a function call between two parts of the same mental model.
  • Logical separation is kept, not lost. Inside the one Express app, auth-related code (routes, controllers, middleware) never imports workspace/task internals directly and vice versa — they only interact through well-defined function boundaries, and the database schema keeps the tables cleanly grouped. This means a future "split into two real services" migration is a refactor, not a rewrite.
  • Consistent with how the rest of the team is structured. The AI Agent Service and Execution & Artifact Service are owned by different people and genuinely benefit from being separate — that's exactly the case microservices are for.

Cross-service communication: the AI Agent Service calls the Workspace & Task Service's API (JWT-authenticated, using a service-level token or the delegating user's token) to fetch task details and report status/results back. The Execution & Artifact Service is called by the AI Agent Service, not directly by Workspace & Task.

5.1 High-Level Data Flow

  1. User registers/logs in → Identity & Access issues a JWT.
  2. User creates a workspace and invites members → Workspace & Task Service.
  3. User creates a task and assigns it to an AI agent → Workspace & Task Service creates a task row and, on assignment, a workflow_runs row with status pending.
  4. AI Agent Service polls or is notified of the new run → fetches task details via API.
  5. AI Agent Service plans steps → calls Execution & Artifact Service to run them.
  6. Execution & Artifact Service runs the action in a sandbox → stores the resulting artifact → returns a reference.
  7. AI Agent Service reports back to Workspace & Task Service → workflow_runs status updated to completed/failed, artifact reference stored.
  8. Frontend polls/reads the task and run status → shows the artifact to the user.

6. Functional Requirements

6.1 Identity & Access Service You

FR-1: User Registration

  • POST /api/auth/register accepts email, password, and (optionally) a display name.
  • Password is hashed with bcrypt before storage — plaintext password is never written to the database or logs.
  • Email uniqueness is enforced at the database level (unique constraint) and checked at the application level for a clean error message.
Acceptance criteria:
  • Valid registration returns 201 Created with a JWT and the created user's non-sensitive fields (id, email, created_at) — never the password hash.
  • Registering with an already-used email returns 409 Conflict with a clear error message, not a raw database error.
  • Missing or malformed email/password returns 400 Bad Request.

FR-2: User Login

  • POST /api/auth/login accepts email + password.
  • Looks up the user by email, compares password against stored hash using bcrypt.compare.
  • On success, issues a new signed JWT and records a session in auth_sessions.
Acceptance criteria:
  • Correct credentials return 200 OK with a JWT.
  • Incorrect password or non-existent email both return the same generic 401 Unauthorized message (never reveal whether the email exists — this is a deliberate security choice, not an oversight).
  • A new row is created in auth_sessions on every successful login.

FR-3: Token Verification Middleware

  • A reusable verifyToken Express middleware reads the Authorization: Bearer <token> header, verifies the JWT signature and expiry, and attaches the decoded user info (e.g. req.user.id) to the request.
  • Applied to every route that requires authentication (all workspace/task routes).
Acceptance criteria:
  • Missing token → 401 Unauthorized.
  • Invalid/tampered signature → 401 Unauthorized.
  • Expired token → 401 Unauthorized with an error code the frontend can use to trigger a re-login.
  • Valid token → request proceeds, req.user populated.

FR-4: Session Management

  • auth_sessions tracks issued sessions (and can later support logout/revocation and viewing active devices).
  • Planned: POST /api/auth/logout to revoke a session; password reset flow.

6.2 Workspace & Task Service You

FR-5: Workspace CRUD

  • Authenticated users can create a workspace (they become its first member, with an owner-level role).
  • Users can list workspaces they belong to, view a single workspace's details, update its name/description (owner/admin only), and delete it (owner only, soft delete recommended).
Acceptance criteria:
  • Creating a workspace also creates the corresponding workspace_members row for the creator with role owner.
  • A user who is not a member of a workspace gets 403 Forbidden when trying to read/write it, not 404 (avoids leaking existence — or 404 is also acceptable if the team prefers not to reveal existence at all; pick one convention and document it).

FR-6: Workspace Membership

  • Owners/admins can invite a user (by email) to a workspace, remove a member, or change a member's role.
  • Roles: owner, admin, member (exact set to be finalized, but at minimum owner vs. member).

FR-7: Task Management

  • Any workspace member can create a task within that workspace: title, description, assignee (a user or an AI agent identifier), due date (optional), priority (optional).
  • Tasks can be listed, filtered by status/assignee, updated, and deleted within a workspace.
  • Task status lifecycle: pending → in_progress → completed, with a failed branch when assigned to an AI agent and execution fails.

FR-8: Task Dependencies

  • A task can declare one or more other tasks as prerequisites via task_dependencies.
  • A task assigned to an AI agent should not be picked up for execution until all its dependencies are completed.
Acceptance criteria:
  • Attempting to create a circular dependency (A depends on B, B depends on A) is rejected with 400 Bad Request.

FR-9: Workflow Runs

  • When a task is assigned to an AI agent, a workflow_runs row is created representing one execution attempt.
  • The AI Agent Service updates a run's status (pending → running → completed/failed) and result via an authenticated API call.
  • A task can have multiple workflow runs over time (e.g. a retry after failure).

6.3 AI Agent Service Team

  • Receive a task definition (fetched from the Workspace & Task Service) for a given workflow_run.
  • Interpret the task and plan a sequence of actions/tool calls needed to complete it.
  • Invoke the Execution & Artifact Service to carry out each planned action.
  • Report progress and final status (and any resulting artifact reference) back to the Workspace & Task Service.
  • Detailed requirements to be authored by the owning teammate; this PRD defines the integration contract only (Section 9).

6.4 Execution & Artifact Service Team

  • Execute agent-requested actions in an isolated/sandboxed environment (no access to other users' data).
  • Store resulting artifacts (files, structured output, logs) with metadata: owning task/run, creation time, content type.
  • Expose artifacts for retrieval by the frontend or other services, with the same authentication model as the rest of the system.
  • Detailed requirements to be authored by the owning teammate.

6.5 Frontend Team

  • Auth screens (register/login), storing the JWT and attaching it to subsequent API calls.
  • Workspace dashboard: list/create workspaces, manage members.
  • Task board: create tasks, view status, view dependency chains, assign to a human or an AI agent.
  • Artifact viewer for completed workflow runs.
  • Detailed requirements to be authored by the owning teammate.

7. Non-Functional Requirements

CategoryRequirement
SecurityAll SQL via parameterized queries (no string concatenation); passwords hashed with bcrypt and never returned in any API response; JWTs signed with a secret from environment config, never hardcoded; DB accessed via a least-privilege user (app_user), not a superuser.
MaintainabilityMVC separation (routes → controllers → db) so auth logic and workspace/task logic stay decoupled inside one app; consistent naming and error-response shape across all endpoints.
DocumentationEvery architectural and technical decision recorded in docs/PROGRESS.md as it is made, including the reasoning, not just the outcome.
ReliabilityPostgreSQL connection pooling to handle concurrent requests without exhausting connections; graceful error responses instead of unhandled exceptions/crashes.
PortabilityEnvironment-based configuration via dotenv (DB credentials, JWT secret, port) so the app behaves identically across dev machines and, eventually, a deployment environment.
Performance (indicative, non-binding for a student project)Typical API responses under ~200ms on local hardware for simple CRUD; no N+1 query patterns for listing tasks/members.
Auditabilityauth_sessions and workflow_runs provide a basic audit trail of who logged in when, and what an agent did and when.

10. Error Handling & Status Codes

StatusUsed when
200 OKSuccessful GET/PATCH
201 CreatedSuccessful POST that creates a resource
400 Bad RequestValidation failure (missing field, wrong type, circular dependency, etc.)
401 UnauthorizedMissing/invalid/expired JWT, or bad login credentials
403 ForbiddenAuthenticated but not authorized (e.g. not a workspace member)
404 Not FoundResource does not exist (or is hidden intentionally — pick one convention, see FR-5)
409 ConflictDuplicate email on registration, duplicate workspace membership
500 Internal Server ErrorUnexpected server-side failure — always logged, never leaks internals to the client

Every error response follows the same shape: { "error": "MACHINE_READABLE_CODE", "message": "human readable" }. This lets the frontend branch on error without parsing free text.

12. Testing Strategy

  • Manual API testing during development (curl / Postman / Thunder Client) — this is how register was verified and how login and the duplicate-email case will be verified next.
  • Unit tests for pure logic: password hashing wrapper, JWT sign/verify wrapper, circular-dependency detection for tasks. (planned, not yet started)
  • Integration tests against a real (test) PostgreSQL database for each endpoint's happy path and key error paths (400/401/403/404/409).
  • Cross-service testing once the AI Agent Service is ready: a mock/stub workflow run update to confirm the Workspace & Task Service accepts and stores it correctly.

13. Deployment & Environment

  • Local development: PostgreSQL running locally via Fedora's dnf-installed package, app run with node directly (or nodemon for auto-restart during development).
  • Configuration: all secrets and environment-specific values (DB host/user/password, JWT secret, port) live in a .env file, loaded via dotenv, and are never committed to source control.
  • Database user: the app connects as the low-privilege app_user, not a PostgreSQL superuser — limits blast radius if credentials ever leak.
  • Production/demo deployment: to be decided by the team — options include a single VM running all backend pieces, or containerizing each service with Docker for the final demo.

16. Assumptions, Constraints & Risks

  • Assumption: teammates' services will expose stable HTTP APIs that the Workspace & Task Service can call synchronously (no message queue in v1).
  • Constraint: a single developer for two of four backend services limits parallel velocity on that side of the system — realistic milestone pacing should account for this.
  • Risk: integration between independently-built services (auth token format, request/response shapes) may drift if not agreed early — mitigated by publishing Section 9's contracts to the team before each service is built.
  • Risk: consolidating two services into one app is a deliberate deviation from the original spec; worth flagging explicitly to the instructor/grader, with the reasoning in Section 5 as justification.
  • Risk: circular task dependencies or orphaned workflow runs (e.g. agent crashes mid-run) need explicit handling, not just happy-path code.

17. Success Criteria

  • A user can register, log in, create a workspace, create a task, and see it executed by an agent with a resulting artifact — all through the frontend.
  • No plaintext passwords or sensitive data ever appear in API responses or logs.
  • All database queries are parameterized; the schema enforces referential integrity via foreign keys.
  • Every error case in Section 10 returns the correct status code and a consistent error shape.
  • docs/PROGRESS.md reflects and explains every major decision made during the build, in enough depth that Harendra could re-derive the reasoning months later.

18. Glossary

TermMeaning
WorkspaceA container for a group of users and their tasks — roughly analogous to a "project" or "team space".
TaskA single unit of work, assignable to a human or an AI agent.
Workflow RunOne execution attempt of a task by an AI agent; a task can have multiple runs over time.
ArtifactAny output produced by an agent's execution — a file, a report, structured data — stored by the Execution & Artifact Service.
JWTJSON Web Token — a signed (not encrypted) token proving who a user is, without the server needing to store session state for every request.
bcryptA one-way password hashing algorithm — passwords are hashed, never encrypted, because hashing cannot be reversed even by the server.
